Skill 匹配与沉淀

本文是 README 深入文档索引「Skill 匹配与沉淀」条目的完整版。

Skill 按 builtin -> user -> project 加载，同名时后层覆盖前层：

  • builtin：产品默认能力
  • user：~/.nexuscli/skills/*/SKILL.md（原生格式，跨项目复用）；另扫描 Agent Skills 规范标准目录 ~/.agents/skills/
  • project：.nexuscli/skills/*/SKILL.md（原生格式，最贴近当前仓库）；另扫描规范标准目录 .agents/skills/

每层内部扫描顺序是标准目录在前、原生目录在后，所以同层同名时原生 .nexuscli/skills 目录的 Skill 胜出（规范目录的价值在于让生态里的标准 Skill 包原样加载，不改文件即可用）。

frontmatter 在 name / description / tags / version 之外还接受两个 Agent Skills 规范字段（连字符与下划线两种写法都认）：

  • allowed-tools：逗号分隔字符串（规范写法，如 Bash(git:*), Read）或内联列表。load_skill 把 Skill 正文注入上下文时会附一行「该技能激活期间允许的工具」提示；如实边界：这是提示性约束，执行器不做硬限制，真正的工具白名单仍由代理 frontmatter 的 tools 控制。
  • disable-model-invocation：true / 1 / yes 时该 Skill 退出自动 Top-K 匹配候选（模型不会被提示去加载它），但 /skill load 命令与显式 load_skill 调用照常可用——挡的是自动候选，不是加载通道。

L0/L1/L2 分层加载

Skill 上下文分三层（内容抽象层级思路来自 OpenViking，L0 → L1 → L2 逐层加深）：

  • L0 abstract：frontmatter 可选 abstract: 一行，给候选阶段的「更强一句话」。候选行有 abstract 时用它替换 description（二者并存浪费 token），没写则回落 description；Top-K 匹配始终用 description 打分，abstract 不参与匹配，所以加 abstract 不会改变排名。
  • L1 overview：frontmatter 可选 overview:（| 块的多行会折叠成一行）。缺省自动生成：取正文首段（首个 ## 小节之前的第一段，跳过开头 H1 标题），折叠一行、500 字符截断；自动生成的概览会标注 generated——load_skill 的 overview 返回正文带 [overview; generated from the skill body]，/skill list 层列显示 L1:gen（显式声明为 L1:+，无正文可生成时 L1:-）。
  • L2 全文：load_skill 的默认行为（level: full），与历史行为逐字节一致，含 5000 字符截断。

frontmatter 字段参考（均为可选，缺省行为与历史版本一致）：

字段 写法 作用
abstract 单行字符串 L0 候选行文本；缺省回落 description
overview 单行或 \| 块 L1 概览；缺省从正文首段生成并标 generated
requirements flow map：{bins: [git, rg], env: [GITHUB_TOKEN]} 可用性过滤：bins 逐个查 PATH（shutil.which），env 逐个查环境变量（非空即满足）；语义改写自 OpenViking vikingbot skills.py 的 _check_requirements，未整搬代码
allowed-tools / disable-model-invocation 见上节 Agent Skills 规范字段

requirements 不满足的 Skill：不进自动候选（不向模型提示一个跑不起来的技能），/skill list 层列标 unavailable (missing: bin: git env: GITHUB_TOKEN) 列出缺失项；显式 load_skill 与 /skill load 仍可用——过滤是候选阶段的决定，不是加载门。内置 web-access Skill 的 frontmatter 是 abstract/overview 的示范写法。

frontmatter 解析同时记录 lint 告警（规则改写自 OpenViking core/skill_loader.py 的校验规则）：name/description 必填、name 字符集与 64 字上限、与目录名一致、description 1024 字上限、正文 500 行告警；未知键容忍不报。告警不改加载行为，只在 /skill list 层列以 warn:<规则码> 显示。

每次用户输入先用 name、description、tags 做中英文词法/字符 n-gram Top-K 匹配，再把候选交给模型决定是否调用 load_skill。load_skill 支持可选 level 参数：full（默认，全文）或 overview（先读一屏 L1 概览省 token，需要细节再 full）；返回文本与 display_summary 带层信息。Skill 正文只在真正加载后进入当前 ReAct 的下一模型轮；每个并发子 Agent 都有独立 Skill 缓冲区，不会串线。

real 轨的 skill 可达性

真模型轨道（nexuscli eval run --real）的只读白名单（eval/real.py 的 REAL_TRACK_TOOLS）包含 load_skill：候选注入 → load_skill → 全文的链路在真实轨道完整可达。此前它被按「用户态写」排除（用量计数器写 ~/.nexuscli/usage.json），分层加载 spec 把这归为误伤：内容面按名字在固定 skill 根解析、只读、无路径参数不可遍历，残余的计数器写属记账性质——没有任何行为决策读它，轨道不变量相应收窄为「零工作区写 + 这一处已声明的用户目录计数器写」。行为场景 examples/evals/real/03_skill_rule_follow.json 用仓库根 .agents/skills/rule-demo/ 演示链路：prompt 点名 skill → 模型调用 load_skill → 遵循其回复格式规则（final_contains 断言 SKILL-RULE-OK 标记）；场景 PASS/FAIL 是 nightly 行为信号，链路可达性由 hermetic 单测保证。

当一次成功流程具备稳定输入、明确步骤和可复用边界时，模型可以调用 save_skill 提议写入 project 或 user 层。该工具默认拒绝覆盖已有 Skill，并强制人工确认。

eval 驱动的提案进化

/skill evolve <name> <rule...> 是纯手写的规则追加；/skill propose 是它的评估驱动版：读取最近一次 eval 报告的失败项与成本告警，交给一次真实 LLM 调用产出结构化改进提案，再经逐条人审落地。两条路径并存，互不改动。

用法

/skill propose <name> [--report hermetic|real]
/skill proposals <name>

propose 默认读 hermetic 轨道报告 <cwd>/.nexuscli/evals/last-report.json，--report real 改读真模型轨道的 last-real-report.json；<name> 必须是 user 层 Skill（~/.nexuscli/skills/<name>/SKILL.md，与 /skill evolve 同边界，builtin/project 不在范围）。三种空转情形都会明确提示而不是静默跳过：报告文件不存在（提示先跑 nexuscli eval run / --real）、报告里没有失败项也没有成本告警、没有可用的 LLM Key（走正常配置链报错，附 NEXUSCLI_API_KEY 等配置指引）。

提案结构与人审语义

一次 LLM 调用收到目标 Skill 全文加报告摘要（失败场景的原因、成本告警），被要求只回一个 JSON 数组，每条形如 {"rule": "<可追加进 ## Evolved Rules 的一条规则>", "evidence": "<引用的报告场景名 + 原因/告警片段>"}。落地前有证据门：evidence 必须对得上报告摘要——命中失败/告警场景名（大小写不敏感），或逐字引用一段足够长的失败原因——对不上的条目直接丢弃，人不会看到无据提案；LLM 回复不是合法 JSON 数组时整体报错，不会拿半成品过审。

人审逐条进行，提示带原因行（Reason: <该条 evidence>，与工具审批弹窗同一规范）；y 落地、n 跳过本条、s 跳过余下；Ctrl+C/Ctrl+D（EOF）视同 s，Esc 不会被拦截——按 Esc 再回车提交的是默认答案 n（只跳过当前条）。两条路都是失败关闭：不敲 y 就不会有任何条目落地。确认项经既有的 SkillEvolutionStore.save_versioned(name, rule, reason="propose") 落地：改动前状态冻结为 skill_history/<name>/v<N>.md 快照（上限 10 个），## Evolved Rules 追加一条带时间戳的规则，audit.jsonl 落一行 op=save——快照、回滚（/skill rollback）、统计（/skill stats）全部复用既有机制。

/skill proposals <name> 列出历史提案记录：时间、条数、落地数、报告轨道与文件路径。

非交互与失败关闭

落地门本身按 sys.stdin.isatty() 判定交互性，是失败关闭的：没有 TTY 可以作答时，提案照常生成并落档，但不会落地任何规则，全部条目记为 pending，并提示回 REPL 里审阅——没有人点头，Skill 就不变。需要如实说明的是，今天并不存在「无 TTY 跑 /skill propose」的生产路径：-p 单次模式只展开自定义斜杠命令，未匹配的 /name 会原样作为普通 prompt 发给模型（entrypoints/cli.py 的 _expand_custom_prompt），管道 stdin 在 REPL 入口就被拒绝（entrypoints/repl.py）。这个门是纵深防御，也是测试注入假答案、验证失败关闭语义的位置。

每次 propose 都会写一条记录到 ~/.nexuscli/skill_history/<name>/proposals/<ts>.json：报告摘要（落地前的快照，供人工对照）、提案全文、每条的人审结论与落地版本号。有落地条目且跑过落地后对比时，同一文件会被原地重写（不会另存新记录），带上 post_landing 字段。

落地后 real-eval 对比（闭环后半环）

真的有条目落地后，REPL 会再问一次「Run the real-eval post-landing diff now?」——这是第二次人工确认：Reason 行写明这是一次真实网关调用，重跑真模型轨道场景 03（03_skill_rule_follow，skill 规则遵循验证器；--file 语义只跑这一个，不跑全量），预估 1-2 万 token。只有敲 y 才执行；n（默认值，任何非 y 答案同）或 Ctrl+C/Ctrl+D 都记 declined，不产生任何网关调用。确认后的调用在 propose.py 的 run_post_landing_diff 里固定四步：

  1. 备份：把 .nexuscli/evals/last-real-report.json 原样读入内存；文件不存在则 before 侧为空，读不出来则直接放弃（没有备份就不跑，绝不裸跑）。
  2. 跑：经 eval/real.py 的 run_real_scenarios 重跑场景 03 并覆写报告——与 eval run --real 同一条链，无 Key 在跑任何场景之前就报错并附 NEXUSCLI_API_KEY 等配置指引。
  3. 对比：落地前报告 vs 新报告中同一场景的 status / pass_k.all_pass / 失败原因，外加两份报告 summary 的 all_pass_rate，写进提案记录 post_landing 的 before/after。
  4. 还原：把备份逐字节写回；原本没有报告的，则把这次跑出的报告删掉、恢复「文件不存在」的原状。

还原是硬保证：nightly 轨道读的就是这个文件，绝不留下单场景报告。还原失败会显式告警并在 post_landing 落 report_restored=false，需要手工恢复后再跑 nightly——绝不静默污染基线。退化路径同样落档：拒绝（declined）、非交互（skipped_reason=non-interactive）、无 Key 或场景文件缺失（errors 带指引）、场景执行异常（errors 落档且仍执行还原）。

如实边界

eval 报告是提案依据，不是落地效果验证器。 hermetic eval 运行时关闭 skill 注入（eval/runner.py 置 features.skill = False 以保证确定性），所以「改了 Skill → hermetic 分数变化」这条因果链不存在；真模型轨道是否开 skill 注入亦不在此依赖内。提案记录保存落地前的报告摘要供人工对照；真模型轨道的落地效果对比由上面的可选 post_landing diff 提供——但单次对比是档案信号，不是门禁：模型遵循率有波动，一次 before/after 不构成统计结论，diff 结果只进提案记录供人阅读，不回写报告、不做回归判定、不触发任何后续动作，「落地→评测→再提案」的无人值守循环仍然不做。也不要指望无监督批量改写：人审是硬门，每条落地都要过一次 y/n/s，效果对比也要再过一次 y/n。
