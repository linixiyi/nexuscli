工作台（Workbench）

本文是 README「🖥️ 可视化工作台」章节的完整版。

工作台是 NexusCLI 的浏览器入口：「一个 Core、多种入口」中的 Web 形态。服务端 = 现有 Runtime API（标准库 http.server，零新增 Python 依赖）+ SSE 事件流 + 静态资源托管； 前端 = frontend/（Vite + React + TypeScript），构建产物 frontend/dist 由服务端托管。

快速开始

仓库检出自带已构建的 frontend/dist，直接可用：

NEXUSCLI_RUNTIME_API_KEY=dev-key uv run nexuscli serve --workbench --port 8080
# 打开终端打印的 http://127.0.0.1:8080/#bootstrap=… 一键链接完成一次性认证

启动时终端会打印 #bootstrap= 一键链接：前端读出 URL 片段里的一次性口令（随即抹除） 换发 HttpOnly cookie 会话；同时该链接会写入 ~/.nexuscli/workbench-link.txt（权限 0600，每次启动覆盖）。直接打开首页而无口令时，认证门支持粘贴一键链接 / 口令换发， 并给出「查启动日志 / 读链接文件」两条恢复路径——服务在后台或他人终端运行时不再依赖 翻日志。口令一次性（已用即 403）；服务重启即生成新口令并刷新链接文件。刷新页面不 影响可写性：csrf 只存内存（cookie 不受影响），前端刷新后自动调 POST /v1/workbench/reissue-csrf 凭会话 cookie 取回当前 csrf——一次性的只有 bootstrap 口令，csrf 可取回且重签不轮换（多标签页互不影响：第二标签页打开不会使 已打开标签页失去写能力）；cookie 已失效（如服务重启）时回落认证门。

自行构建前端（需要 Node.js 22 LTS 与 npm）：

cd frontend && npm ci && npm run build

frontend/dist 缺失时首页显示空态页与构建指引，/v1/* API 不受影响。开发模式下 cd frontend && npm run dev 经 Vite proxy 同源转发 /v1 到 Runtime API（默认 8080， 可用 NEXUSCLI_WORKBENCH_API_PORT 覆盖）。

功能面

  • 布局（2026-10-26 UI 重构，对齐 kitagent 设计语言）：侧栏（品牌 / 新建会话 / 工作会话 + 会话回放两组列表 / 任务与用量入口）+ 顶栏（面包屑、SSE 连接徽章）+ 聊天主面板（markdown 渲染、欢迎页、Enter 发送 / IME 保护 / 草稿持久化）+ 右侧 执行检查器（审批卡、工具时间线、运行报告导出）+ 状态栏
  • 会话视图：工作会话 = 本浏览器线程记忆（SSE since=0 全量回放并可继续观察 进行中的 turn）；会话回放 = REPL 会话 /v1/sessions/{id}/transcript 静态渲染
  • 发起 turn：输入框建线程提交（react/plan/team 三模式），POST 作为后台提交发出， SSE 实时观察流式输出与工具调用；断线退避重连、seq 断档自动重拉快照、刷新后 未确认请求走幂等恢复（查询而非重发）
  • 任务面板：后台任务列表 2s 轮询、详情展开、取消（与 /v1/tasks 数据一致）
  • usage 统计：近 N 天回合数/Token/成本汇总卡与按模型、按来源两张拆分表
  • 审批卡片：挂起审批在执行检查器出现（Reason 行 + 四个决策动词：批准 / 本轮放行 / 切换自动模式 / 拒绝）。「本轮放行」= 批准本次调用并在本次 run 内 放行该工具的后续调用（同 REPL 的 r，ask 规则与 hook 询问仍保留否决权）； 「切换自动模式」= 会话切到 auto/full access，当前等待与后续调用自动允许 （同 REPL 的 a，换模式即清空单项撤销）。审批请求与解决由 SSE 推送 （approval_suspended / approval_resolved 帧），列表刷新以 2s 轮询兜底
  • 慢等待与可辨识（2026-10-27 第二轮 UX）：执行中 30s 无新事件时聊天面板追加 「仍在等待模型响应…」提示（不改变 busy 语义、不自动取消）；无标题 REPL 会话回放 条目回退显示「会话 <日期时间>」；运行报告的「执行事实与来源」逐工具列出，点击 跳转执行详情

端点与 API

工作台消费的端点（鉴权：浏览器走「一次性 #bootstrap 口令 → HttpOnly SameSite=strict cookie → 变更请求（POST）另带 x-csrf-token 头 → Origin 白名单（带 Origin 头且非 本机回环来源一律 403）」三件套；外部通道保留 x-api-key 头，SSE 额外支持 api_key 查询参数。语义详见 runtime-api.md）：

方法与路径 语义
GET /v1/threads/{id}/events/stream?since=N SSE 事件流：回放 + 实时 + 15s 心跳，16 连接上限
POST /v1/workbench/reissue-csrf 凭有效会话 cookie 重签 x-csrf-token（刷新后自动恢复可写；无 cookie 401）
GET /v1/sessions REPL 会话列表（JSONL 首行 meta，updated_at 倒序，cwd 过滤）
GET /v1/sessions/{id}/transcript 会话转录分页读取（id 仅 [0-9a-zA-Z-]+）
GET /v1/usage/summary?days=N usage 聚合（UsageStore.stats 原样形状）
GET /v1/approvals 挂起审批列表
POST /v1/approvals/{id}/decision 审批决策：approve / deny / approve_run（本次 run 内放行）/ approve_auto（切到 auto/full access 并即时重判挂起审批）
GET / 与非 /v1/* 静态资源 / SPA 回退 / 空态页

既有 threads / turns / tasks 端点见 runtime-api.md，不在此重复。

部署边界与安全

  • 服务端硬绑定 127.0.0.1；无多用户认证、不做公网部署（与 MCP server 边界一致）

  • AGPLv3 §13 源码提供义务：本项目按 AGPL-3.0-only 授权。经由网络与该服务交互的用户（浏览器访问工作台、调用 Runtime API 或 MCP server 的客户端），有权获取对应源码——自托管即天然满足（随仓库分发）；若修改后对外提供网络服务，须向你服务的每个用户提供修改版源码（含前端 frontend/ 源码与其构建产物 frontend/dist）。

  • 静态资源免鉴权（无用户数据的构建产物）；/v1/* 全走鉴权（外部 x-api-key 或 bootstrap 换发的浏览器 cookie 会话，cookie 通道的变更请求另须 CSRF）

  • SSE 的 api_key 查询参数会出现在本机浏览器历史（浏览器 EventSource 无法设置自定义 请求头，这是唯一出口）；缓解是仅绑定 localhost 且该端点只读
  • 会话转录端点返回用户对话正文（本机敏感数据），与 nexuscli sessions CLI 同暴露级别
  • 审批挂起超时按 deny 失败关闭：默认 300s，可用环境变量 NEXUSCLI_APPROVAL_TIMEOUT_SECONDS（或 RuntimeApiServer 的 approval_timeout_seconds 参数）调整；超时的卡由服务端看护线程统一收口为 expired（fail-closed deny），执行器把超时 deny 也记为 approver="hitl" （词表无 approval-timeout 值，桥在 resolved_by 里留存真相）

如实边界

  • MVP 无前端单元测试（vitest 挂账）；质量门槛 = tsc -b 构建通过 + Python 侧端点测试 + 真实进程 smoke
  • frontend/dist 已随 wheel 分发（pyproject force-include），NEXUSCLI_WORKBENCH_DIST 仍可覆盖 dist 根
  • Windows 下的前端构建不被 CI 覆盖（frontend job 仅 ubuntu）
  • 截图待补（README 章节内为 HTML 注释占位）
  • 审批卡片列表的刷新以 2s 轮询兜底：服务端已推送 approval_suspended / approval_resolved SSE 帧（线程 scope）且前端事件流已折叠它们 （approval_resolved 在 api.py 收口点落线程 events 表，回放/重建后仍可见， 运行报告「人工决定」计数由它驱动），但「SSE 审批事件到达 → 立即刷新审批列表」 的接线在 App.tsx（2026-11-07 发布加固包 0021 boundary 之外）尚未补上； 任务 scope 的审批卡不在任何线程流内，本就依赖轮询
